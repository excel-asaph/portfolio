Understanding the project.

About

I built Accident Detection as an end-to-end MLOps project. The model is a CNN+LSTM hybrid that analyzes consecutive CCTV frames to determine whether an accident is unfolding. Connected to a FastAPI backend with 11 endpoints, MongoDB GridFS for image storage, and a Streamlit dashboard for predictions and retraining, both deployments are live on Render.

Problem Statement

Most computer vision projects stop at the notebook. Model trained, accuracy noted, done. I wanted to build something that worked as a real system: upload footage, get a prediction, and if the model was wrong, add that footage to the training set and retrain without touching a single line of code. The model is the starting point. The pipeline is the actual project.

_______   WHY THIS PROBLEM IS HARD

Three challenges, not one.

A Single Frame Can't See an Accident

Accidents unfold over time. A car drifting across a lane, the moment of impact, a vehicle stopping suddenly: none of these register in a single image. The signal lives in the change between frames. That's why I chose a CNN+LSTM architecture: MobileNetV2 extracts what each frame looks like, and LSTM layers track how those looks change across a sequence. Standard image classifiers, trained on one frame at a time, simply miss the event entirely.

The Pipeline Matters as Much as the Model

Most computer vision projects stop at the notebook. I wanted to build something that could actually improve over time without touching code. That meant thinking about storage (MongoDB GridFS for images), feedback loops (a /retrain endpoint that pulls from new labeled data), and monitoring (a Streamlit dashboard for non-technical review). The 53.3% accuracy is the starting point. The infrastructure is what turns it into something that gets better.

Scale Can't Be an Afterthought

CCTV systems generate a lot of frames. A real deployment needs to handle concurrent requests, growing datasets, and load spikes. Rather than discovering the limits in production, I built Locust load testing in from the start. Under 50 concurrent users uploading 5-frame sequences, it caught a memory bottleneck in the upload endpoint early. The fix was streaming GridFS writes instead of buffering in memory. Finding it in production would have been significantly more painful.

_______   THE DATASET

CCTV accident footage from Kaggle.

The training data comes from a Kaggle dataset built from YouTube videos of real CCTV accident footage. Each sequence contains consecutive frames from the same event, which is what makes it suitable for temporal modeling. The class balance is roughly even, which kept training stable. The challenge isn't the balance: accident and non-accident frames look visually similar at a glance. The model has to learn the motion pattern across frames, not any single visual signature.

_______   MODEL DESIGN

MobileNetV2 for frames, LSTM for sequences.

I chose MobileNetV2 as the CNN backbone because it's lightweight enough to run on Render's free tier without choking, and the ImageNet pre-training gives it a strong starting point for visual feature extraction. Weights are frozen: MobileNetV2 extracts spatial features per frame, and those feature vectors are fed as a time-distributed sequence into LSTM layers. The LSTM's job is to track how the scene is changing, not just what it looks like at any given moment. A Dense layer with sigmoid output gives the final binary prediction.

_______   FASTAPI ENDPOINTS

11 endpoints across the full pipeline.

I organized the API into four groups: prediction and analysis, training and model management, data management, and system health. The endpoint I was most deliberate about designing was /add-prediction-to-training, which lets you take any prediction the model made and add it directly to the labeled training set. That's the feedback loop that makes the model improvable without writing any new code.

_______   TRAINING RESULTS

Early stopping, scheduling, and an honest 53.3%.

I trained with early stopping and learning rate scheduling on 58 training sequences (grouped consecutive frames), evaluated against 45 test sequences — 23 accident and 22 non-accident. The most interesting result isn't the overall accuracy of 53.3%. It's the confusion matrix breakdown: TN=1, FP=21, FN=0, TP=23. The model caught every single accident in the test set (100% recall) while flagging 21 out of 22 non-accident sequences as accidents. In a real CCTV surveillance context, that calibration is arguably correct: a false alarm triggers a human review; a missed accident costs lives. The model is safety-first by nature, not by tuning. That said, the precision of 52.3% means operators would be reviewing a lot of false alerts, which is the real problem to solve in the next iteration.

LEARNINGS

_______   KEY FINDINGS

What I learned building a real MLOps system.

"53.3% is a number I could hide if I chose different charts. I'm not going to. The dataset is genuinely hard, and the model is a starting point. What I'm actually proud of here is the system: a pipeline that can ingest new footage, retrain, and ship an improved version without touching a line of code."

What worked well

The infrastructure decisions held up well. MongoDB GridFS handled image storage cleanly across all three layers of the system, and the /retrain endpoint worked exactly as I designed: upload new labeled data, hit the endpoint, get an updated model. That feedback loop is the whole point of the project, and it works.

The Locust load testing was the smartest thing I built in from the start. Under 50 concurrent users uploading 5-frame sequences, it surfaced a memory bottleneck in the upload endpoint before the system went anywhere near real traffic. The fix was straightforward: stream GridFS writes instead of buffering uploads in memory. Without the test, that bug would have appeared the first time someone used the system seriously. Deploying both the FastAPI backend and the Streamlit dashboard on Render's free tier also worked better than expected. Cold-start latency is noticeable, but for a demo system it's entirely acceptable.

What I would do differently

The most obvious next step is fine-tuning. MobileNetV2's weights are frozen in the current implementation, which means the CNN is doing ImageNet feature extraction, not CCTV-specific feature extraction. Unfreezing the top layers and fine-tuning on accident footage directly would likely improve accuracy significantly. It would also need a larger labeled dataset to avoid overfitting, which points to a second gap: the training data is still relatively small for a temporal classification task.

The other thing I would change is interpretability. When the model mispredicts, I have no good way to understand why. Adding attention visualization over the time dimension would show which frames in the sequence drove the prediction, and per-frame confidence scores would tell me whether the error came from the spatial extraction or the temporal aggregation. That kind of visibility would make iterating on the model substantially faster, and it's something I would build in from day one next time.
