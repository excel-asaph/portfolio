_______   PROJECT DETAILS

Understanding the project.

About

TravelBot is a domain-specific chatbot built by fine-tuning Google's T5 transformer on 20,000 travel and geography query-response pairs from the BAAI/IndustryInstruction dataset. It answers questions about destinations, cultures, transport routes, and geographical features. It also knows its own limits: questions outside the travel and geography domain get a clear refusal rather than a hallucinated response. A FastAPI backend serves predictions and a Streamlit interface provides a conversational front end.

Problem Statement

General-purpose language models are impressive because they can answer almost anything. That breadth is also their weakness for specialized use cases. I wanted to build something specifically good at one thing and honest about what it didn't know. The OOD detection system is not an afterthought: it is the feature that makes the model actually trustworthy. A chatbot that sometimes answers correctly but sometimes fabricates with equal confidence is harder to rely on than one with clearly defined limits.

PROBLEM & CONTEXT

Fine-tuning is the difference between a model that knows about travel and one that's actually good at answering travel questions.

_______   WHY SPECIALIZATION MATTERS

Three things that shaped how I built this.

General Models Generalize. Domain Models Specialize.

A general LLM trained on everything knows about travel the same way it knows about medicine or law. That breadth is useful, but it comes with a cost: the model has no real concept of where its travel knowledge ends. Fine-tuning on 20,000 curated travel Q&A pairs shifts the model's probability distributions toward travel-specific vocabulary, phrasing, and facts. After training, the model doesn't just know about travel; it reasons about it more reliably. Specialization is a feature, not a limitation.

The Metric You Choose Changes What You Build

BLEU measures word overlap. If TravelBot says "The Eiffel Tower is located in France" but the reference says "The Eiffel Tower stands in Paris, France", BLEU penalizes that response despite it being semantically correct. BERTScore computes cosine similarity in contextual embedding space, which captures meaning rather than surface form. I chose BERTScore as the primary metric before running any experiments, because I was optimizing for semantic accuracy. That single decision changed which hyperparameter configuration appeared best.

A Model That Knows When to Say No Is More Useful

Before OOD detection was added, TravelBot would attempt to answer anything. Ask it about cooking or programming and it produced fluent text that looked like an answer but was complete fabrication. Fine-tuned models don't learn to refuse; they learn to generate. The OOD system runs before the T5 inference call. If a query's embedding falls below the domain similarity threshold, the model returns a polite refusal instead of generating a response. Trustworthiness isn't just accuracy on in-domain questions.

_______   THE DATASET

20,000 curated travel and geography pairs.

The training data comes from the BAAI/IndustryInstruction_Travel-Geography dataset, a multilingual instruction set for travel and geography Q&A. I extracted 20,000 English-language pairs and applied text normalization, lemmatization, and T5 input formatting: "question: {query}" as input, the answer as the target. The vocabulary covers destinations, cultural context, transportation, geographical features, and accommodation. The word cloud shows what the model actually spent most of its attention on.

_______   THE MODEL

Why T5 was the right choice for this task.

T5, or Text-to-Text Transfer Transformer, frames every NLP task as a text-to-text problem. Fine-tuning input looks like "question: What is the best time to visit Bali?" and the target is the answer. That uniformity means the same architecture, loss function, and training loop works regardless of task type. T5-base has 220 million parameters, which is large enough to represent complex travel and geography knowledge but manageable enough to deploy without specialized infrastructure. The pre-trained encoder already has strong geography knowledge from training on C4; fine-tuning specializes it for travel Q&A without erasing that foundation.

_______   HYPERPARAMETER SEARCH

Five learning rates, one clear winner.

I ran the experiments in two stages: first fixing batch size and epochs to sweep learning rates, then fixing the learning rate to explore batch size and epoch count. The clear winner across both was batch=8, epochs=3, LR=5e-5. Higher rates caused loss spikes; lower rates converged too slowly within the compute budget. Smaller batch sizes produced less stable gradients; larger ones hurt generalization slightly. A third round tested generation parameters: max_length, beam count, and repetition penalty.

RESULTS & EXECUTION

_______   EVALUATION RESULTS

Performance across five metrics.

The best model, trained at 5e-5, achieved BERTScore F1 of 0.84, which is the metric I care most about for open-ended conversational Q&A. ROUGE-L of 0.47 and BLEU of 0.25 are both lower, but that's expected: conversational travel responses rarely match word-for-word with reference answers. Someone can describe the best time to visit Bali with completely correct information while using entirely different phrasing. BERTScore captures that semantic equivalence in a way the other metrics miss, and 0.84 means TravelBot's responses are genuinely close to ground truth even when the words differ.

_______   OOD DETECTION

The model that knows when to say no.

The OOD detection layer runs before the T5 inference call. If the generated response is too short (under 20 words), it's a signal the model doesn't know what to say about the topic, and the system returns a polite refusal rather than surfacing the short hallucinated output. Simple as the heuristic sounds, it achieved 92% detection accuracy on the out-of-domain test set: 5% false positives (in-domain queries incorrectly refused) and 8% false negatives (off-topic queries that slipped through). A length-based threshold works here because travel and geography answers are inherently descriptive, and a genuine model failure on those topics tends to produce short, vague sentences rather than coherent responses.

LEARNINGS

_______   KEY FINDINGS

What I learned building a specialized NLP system.

"0.84 BERTScore looks clean until you sit with the model and notice it confidently states the wrong rainy season for a destination. The metric measures semantic similarity, not factual correctness. That gap between similarity and accuracy is something no NLP metric handles well, and it's the thing I would take most seriously if I built this again."

What worked well

The BERTScore result is genuinely strong for open-ended conversational Q&A. I wasn't certain 5e-5 would be the clear winner going into the experiments, but the gap between that configuration and the others was consistent across all five metrics, which made the choice unambiguous.

The OOD detection system works exactly as designed. During testing it cleanly refused cooking questions, programming questions, and medical questions every single time. That reliability matters because it is the feature that makes the chatbot actually usable rather than just demonstrable. A model with clearly defined limits is more honest than one that tries to answer everything and occasionally makes things up. FastAPI and Streamlit together gave a complete deployable stack without a lot of overhead, and the integration between the two worked more smoothly than I expected going in.

What I would do differently

The dataset is 20,000 pairs, which covers common destinations well but gets thin on niche geography. The model handles Bali and Kilimanjaro confidently. Ask it about a lesser-known lake in central Africa or a mountain pass in the Karakoram and the answers get noticeably vague. More data from travel forums, guidebooks, and geographic reference sources would address this more directly than any architectural change.

The other thing I would build in from the start is multi-turn conversation memory. Right now each question is answered in isolation: the T5 input doesn't include conversation history, so follow-up questions don't connect logically to what was just discussed. Concatenating the last two or three turns into the input context would make the chatbot feel like an actual conversation rather than a series of independent lookups. The OOD threshold is also a fixed value tuned by hand. Calibrating it against a held-out OOD set would make it more reliable at the edges of the domain, where the current threshold sometimes over-refuses borderline travel questions.
